Step 3 — POD Credential Construction

The TLSNotary attestation is converted into a Zupass POD (Provable Object Data) structure. Each field is hashed into a Poseidon Merkle tree and the root is signed locally.

// POD Credential — key-value structure with Poseidon Merkle commitment pod OctopusTransitCredential { owner_pubkey: "babyJubJub:0x7a3f...c291", zone: "KOWLOON", period: "2026-03", transit_count: 6, // PRIVATE witness mgmt_fee_total: 300, // PRIVATE witness category: "TRANSIT", provenance_hash: "0x5d8c...f024", // commitment to TLSNotary sig // Poseidon Merkle root (commits all entries) merkle_root: "0x3b7e...a918", issuer_signature: "EdDSA:0x1f4a...d602" }

Step 4 — Semaphore V4 Identity Layer

The cardholder proves ownership of the POD without revealing their identity. A deterministic nullifier prevents double-use while remaining unlinkable across different verifiers.

// Semaphore V4 — EdDSA on BabyJubJub curve struct SemaphoreIdentity { secret_key: "*** PRIVATE — never leaves device ***", public_key: "(Bx: 0x7a3f...c291, By: 0x2e8d...f047)", merkle_proof: "[0x4c1a..., 0x8f3b..., ...]", // group membership } // Nullifier — deterministic per (identity, scope) nullifier = Poseidon(secret_key, scope_hash) = "0xd4e8...b192" // Properties: // • Same identity + same scope → same nullifier (prevents double-use) // • Different scopes → different nullifiers (cross-verifier unlinkability) // • Nullifier reveals NOTHING about secret_key
Ownership proven Nullifier registered Identity hidden from verifier

Step 5 — GPC Circuit Configuration & Mopro Proving

The declarative GPC config specifies the claim predicate. Mopro compiles the Groth16 prover to native ARM and generates the proof entirely on the cardholder's smartphone.

// GPC Claim: "transit_count in KOWLOON during 2026-03 ≥ 5" gpc_config MobilityThresholdProof { pod_entry = transit_count, constraint = GTE(5), // private: actual value = 6 ✓ revealed_fields = ["zone", "period"], // everything else stays private nullifier_scope = "transport_dept_subsidy_2026Q1" }

Step 6 — EAS On-chain Attestation (Arbitrum One)

The proof is submitted to the ZKOctopusResolver contract on Arbitrum One. After on-chain verification, an EAS attestation is issued and stored permanently.

// ZKOctopusResolver.sol — on-chain verification function attest(AttestationRequest calldata req) external returns (bytes32) { // 1. Decode attestation data (proof, pubInputs, nullifier) = abi.decode(req.data, ...); // 2. Verify Groth16 proof via BN254 precompile require(verifier.verifyProof(proof, pubInputs), "invalid proof"); // 3. Check nullifier not already used require(!usedNullifiers[nullifier], "double-use"); usedNullifiers[nullifier] = true; // 4. Issue EAS attestation return eas.attest(req); // ~200,000 gas ≈ $0.02–0.04 }

Privacy Comparison
How does ZK-Octopus compare to traditional data sharing for the same urban coordination task?
The Two-Class Problem: Octopus cardholders whose daily spending exceeds HKD 3,000 or annual spending exceeds HKD 25,000 are required to register the card against a Hong Kong Identity Card number. For these users, any raw data transfer to a third party is not a probabilistic re-identification risk — it is a direct disclosure of a named individual's complete movement and payment record. ZK-Octopus addresses both user classes through the same mechanism: verifiers receive only the boolean predicate output, never the underlying data.
